# Controlled deserialization-boundary experiment

## Research question

When a relevant environment mismatch should cause a persisted artifact to be
rejected, can verification prevent the serialized object from being
reconstructed?

## Fixture

The experiment uses a deliberately controlled Python object whose reconstruction
creates a marker file in the CI runner's temporary directory. The marker is a
harmless observation mechanism; the fixture performs no network access, process
execution, privilege changes, or modification outside that marker.

## Protocol

1. Persist the controlled fixture with Modelstamp/joblib.
2. Deterministically introduce a relevant joblib-version mismatch in the
   unsigned reference manifest.
3. Call `modelstamp.load(..., strict=True)`.
4. Record whether the load is rejected and whether the marker exists.
5. Reset the marker and call conventional `joblib.load()` on the same
   serialized artifact.
6. Record whether reconstruction creates the marker.

The experiment asserts only the boundary property:

- strict Modelstamp rejection occurs before the fixture is reconstructed;
- conventional joblib deserialization reconstructs the fixture.

## Scope

This is **not** a malware-detection experiment and does not claim that Modelstamp
makes pickle/joblib safe for untrusted artifacts. It tests ordering: whether a
verification failure can stop execution before crossing the deserialization
boundary.

Results are generated by CI and should not be inferred from this protocol before
execution.
